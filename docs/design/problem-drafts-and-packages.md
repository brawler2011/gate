# RFC: Черновики и сборка пакетов задач

- **Статус:** Предложение для обсуждения
- **Связанная задача:** [#109](https://github.com/brawler2011/gate/issues/109)
- **Дата:** 2026-11-09

## 1. Контекст и границы

У проекта нет пользователей и production-развёртывания. Обратная совместимость, перенос существующих данных и чтение старых пакетов не требуются. Допустимы ломающие изменения БД, API, GFMT и ключей S3 с одновременным обновлением всех потребителей; при внедрении можно сбросить локальные и тестовые данные.

Сейчас изменение файла черновика скачивает, распаковывает и перепаковывает целый ZIP в памяти. Новая модель разделяет редактирование и сборку: **Draft → Build → Package**. Сохранение метаданных и текста не обращается к S3. Полная сборка запускается по явному запросу автора.

В первой реализации используются PostgreSQL как очередь заданий, временные файлы на диске и последовательный pipeline на сборку. Отдельный брокер, распределённый кэш, инкрементальная сборка и дедупликация объектов не нужны.

## 2. Инварианты

1. PostgreSQL хранит единственное редактируемое представление задачи. В Draft нет `problem.yaml`.
2. Build содержит долговечный неизменяемый снимок, зафиксированный при запросе сборки. Воркер не читает текущий Draft.
3. Package существует только после успешной сборки и подтверждённой загрузки архива. Package и его содержимое неизменяемы.
4. Рабочая ссылка на объект S3 создаётся только при состоянии объекта `available`. Временное удержание загрузки может ссылаться на `uploading`, но не даёт права читать её как готовый файл. Все изменения ссылок и GC синхронизируются через запись объекта в PostgreSQL.
5. Контест, submission и judge job закрепляют конкретный Package. Условия, лимиты и scoring берутся из этого пакета или его снимка.
6. Крупные файлы не материализуются целиком в Go heap. Ограничиваются также диск, объём вывода, число файлов и параллелизм.

Транзакции PostgreSQL не охватывают S3. Протокол допускает временные объекты без потребителей, но не публикует ссылки на незавершённые загрузки. Доступность S3 и сохранность объектов обеспечиваются инфраструктурой; имя с хешем не даёт абсолютной гарантии консистентности.

## 3. Модель данных

Ниже — логическая схема; конкретный DDL должен реализовать указанные ограничения.

| Таблица | Содержимое |
|---|---|
| `problems` | Идентичность задачи, организация и права доступа |
| `problem_drafts` | `problem_id`, `revision`, title, short_name, тип, лимиты, max_score и выбранные компоненты |
| `problem_draft_files` | `problem_id`, нормализованный `path`, текст UTF-8 |
| `problem_draft_components` | Идентификатор, роль, путь исходника, язык/компилятор и зависимости |
| `problem_draft_subtasks` | Идентификатор, порядок, имя, политика `complete/each`; баллы вычисляются как сумма весов тестов |
| `problem_draft_subtask_dependencies` | Направленные зависимости подзадач |
| `problem_draft_tests` | Идентификатор, порядок, подзадача, sample, явный вес с точностью до 0.01, описание входа и ответа |
| `problem_draft_assets` | Путь и ссылка на бинарный ресурс условия в S3 |
| `stored_objects` | UUID, организация, назначение, ключ S3, полный SHA-256, размер, состояние, срок загрузки, время потери последних ссылок |
| `problem_builds` | UUID, задача, ревизия, неизменяемый снимок JSONB, версия схемы снимка, digest toolchain, состояние задания, lease, попытки, диагностика |
| `problem_build_objects` | Ссылки с ролью `input` для снимка или `output` для временного удержания результата; у `output` обязателен token попытки |
| `problem_packages` | UUID, задача, `build_id UNIQUE`, ссылка на объект ZIP и время публикации |
| `request_idempotency` | Организация, операция, ключ, отпечаток запроса, lease, назначенная загрузка и результат HTTP-операции |

Build совмещает снимок и задание очереди; отдельная таблица снимков и внешний Outbox для запуска сборки не требуются. Package — только успешный результат, без состояний `pending/failed` и пустых хешей. Реестр объектов хранит ручные тесты, бинарные ресурсы и архивы; отдельная сущность Artifact не нужна.

Все связи проверяют принадлежность одной задаче/организации, где применимо. Ссылки на объекты и используемые пакеты защищены FK с `ON DELETE RESTRICT`. Изменяемые каталоговые поля не используются как метаданные опубликованного пакета; существующий триггер захвата метаданных из `problems` заменяется чтением снимка Build.

Неизменяемость снимка, входных ссылок Build, настроек toolchain и полей Package обеспечивается ограничениями/триггерами БД. У объекта после регистрации неизменяемы UUID, организация, ключ, SHA-256 и размер; меняются только поля жизненного цикла. Удаление после retention разрешено по протоколу GC.

### 3.1. Редактирование

Каждая операция изменения Draft в короткой транзакции блокирует строку `problem_drafts`, проверяет переданную клиентом `expected_revision`, меняет связанные данные и увеличивает ревизию. Несовпадение возвращает `409 Conflict`. Все пути записи, включая импорт, соблюдают этот порядок. Многофайловое изменение, требующее целостности, выполняется одной операцией.

Текст хранится в PostgreSQL; для файла и всего черновика заданы ограничения размера. Заголовок задачи принадлежит метаданным Draft: редактор и рендер условия используют его, а не вторую редактируемую копию внутри Markdown. Изображения, PDF и другие бинарные ресурсы хранятся как объекты S3.

### 3.2. Тесты и компоненты

- Вход теста: либо `manual(input_object_id)`, либо `generator(component_id, args TEXT[], seed)`. `CHECK` обеспечивает взаимоисключение вариантов. Генератор запускается через argv без shell; запись `gen 10 20 > $` может быть только представлением в UI. Способ передачи seed определён контрактом генератора и входит в снимок.
- Для обычных задач ответ задаётся как `generated(main_solution_id)` либо `provided(answer_object_id)`. Выбор явный; существующий ответ не перезаписывается молча. Пустой файл допустим и отличается от отсутствующего.
- Для interactive-задач используется отдельный режим: главное решение взаимодействует с интерактором, обязательного обычного `.ans` нет. Формат пакета явно хранит режим проверки и необходимые данные интерактора.
- Оценивание соответствует модели Polygon: каждому тесту явно назначен неотрицательный вес с точностью до 0.01. `each` суммирует веса пройденных тестов; `complete` начисляет сумму весов тестов группы только при прохождении всей группы. Вес группы и `max_score` вычисляются из весов тестов; автоматического деления баллов группы на число тестов нет. Итог хранится и передаётся в баллах задачи, без нормализации к 100 и без неявного округления авторских весов. PostgreSQL использует точный `numeric`, внутренние расчёты — целые сотые доли; двоичная арифметика float не используется для суммирования весов.
- В первой версии тест принадлежит одной подзадаче. Зависимости подзадач задают условие начисления баллов, но не копируют тесты между группами. Проверяются отсутствие циклов, корректность баллов и единая семантика scoring в Builder и Judge.
- Порядок тестов положителен и уникален в задаче; перенумерация использует отложенную проверку уникальности. Участие sample в оценке определяется конфигурацией его подзадачи.
- Выбранные checker, validator, interactor и main solution ссылаются на компоненты нужной роли. Снимок включает настройки компиляции и все библиотеки. Неполный Draft можно сохранить; перед сборкой проверяется обязательность компонентов для выбранного типа задачи.

### 3.3. Общий транзакционный контракт

Транзакции протокола используют `READ COMMITTED`. При необходимости нескольких блокировок порядок один: запись идемпотентности → Draft → Build → Package → объекты по UUID. Пропускаются не участвующие в операции сущности. Блокировки берутся через `SELECT ... FOR UPDATE` и удерживаются до коммита; сетевых запросов и выполнения Sandbox внутри транзакции нет.

Добавление, замена и удаление любой ссылки блокируют её владельца и все затронутые объекты в этом порядке. После получения блокировки объекта его состояние и наличие ссылок проверяются отдельным SQL-запросом с новым снимком видимости. Проверка ссылок в том же SQL-операторе, который ожидает блокировку, не используется. В частности, один FK не заменяет проверку состояния объекта перед созданием ссылки.

Первая ссылка сбрасывает `unreferenced_at`; удаление последней устанавливает его по времени БД. Это происходит вместе с изменением ссылок в одной транзакции. Lease и сроки загрузок проверяются по текущему времени БД после получения блокировок. Неизвестный результат коммита разрешается чтением устойчивого идентификатора операции; уже зафиксированный результат не заменяется сообщением об ошибке.

## 4. Объекты S3 и загрузка

**Физический ключ объекта — UUID, SHA-256 — контрольная сумма содержимого.** Например, `objects/{organization_id}/{object_id}`. Ключ никогда не переиспользуется, в том числе после удаления. Дедупликации и чистого CAS по SHA-256 в первой версии нет: они не нужны для устранения перепаковки и усложняют согласование повторных загрузок с GC. Короткий хеш пакета остаётся доступен для UI.

1. Backend принимает поток в ограниченный временный файл на диске, одновременно считая SHA-256 и размер. Превышение квоты или обрыв прекращают операцию.
2. В БД создаётся `stored_objects(state = uploading)` с новым UUID, известными SHA-256 и размером, конечным сроком загрузки и начальным `unreferenced_at`. Для результата сборки в той же транзакции под блокировкой Build проверяется lease и создаётся временное удержание `output` с token попытки.
3. Файл загружается по уникальному ключу без перезаписи. Backend проверяет успешное завершение и контрольную сумму средствами выбранного S3-провайдера; ETag не считается SHA-256.
4. В короткой транзакции backend сначала блокирует запись идемпотентности и Draft, затем объект согласно §3.3. Проверяются token операции, ревизия Draft, состояние `uploading` и срок загрузки. Переход в `available`, создание ссылки, увеличение ревизии и сохранение результата HTTP-операции выполняются одним коммитом. При конфликте эта транзакция не публикует объект: он остаётся `uploading` без рабочей ссылки до закрытия/GC. Для ZIP вместо редактирования Draft применяется финальная транзакция §6.

Повтор изменяющего HTTP-запроса с тем же ключом идемпотентности возвращает прежний результат. Общая таблица идемпотентности хранит организацию/операцию/ключ, отпечаток запроса, состояние, результат и назначенный UUID загрузки; запись резервируется до выполнения, а успешный результат фиксируется вместе с изменением. Повтор с другим содержимым отклоняется. Незавершённая операция имеет lease с token: после сбоя её можно повторить, а прежний исполнитель теряет право финализации. Потерянный ответ разрешается чтением результата, а не созданием второго теста.

Если результат записи S3 неизвестен, объект остаётся `uploading` до проверки или истечения срока. Успех подтверждается наличием завершённого объекта с ожидаемыми размером и SHA-256; если провайдер не позволяет проверить checksum метаданными, файл проверяется потоковым чтением. Просроченную загрузку нельзя завершить в БД. Возобновление подтверждает исходные байты, а не перезаписывает ключ; новая попытка после закрытия загрузки использует новый UUID. Проверка checksum не доверяет одному лишь значению, присланному клиентом.

S3 доступен только backend/worker/GC. Авторизация проверяется по потребителю и организации, а не по знанию UUID или хеша. Права приложения и условная запись запрещают перезапись; право удаления выделено GC. WORM/Object Lock не является обязательным механизмом этой архитектуры.

## 5. Снимок и очередь сборки

`POST /problems/{id}/packages/build` принимает ожидаемую ревизию и ключ идемпотентности.

В одной короткой транзакции обработчик блокирует запись идемпотентности и ту же строку Draft, что и редакторы, проверяет ревизию и читает **все** данные сборки после получения блокировки. Пока она удерживается, ни один редактор не может изменить состав черновика. Из прочитанных данных один раз формируется типизированный снимок: метаданные, текст файлов, компоненты, тесты, подзадачи, ресурсы и настройки генерации.

Этот снимок сериализуется в версионированный JSONB `problem_builds`. Из того же значения извлекается полный набор UUID входных объектов и записывается в `problem_build_objects(role = input)` с FK. Отложенный constraint trigger БД проверяет точное равенство набора объектов в снимке и входных ссылках; несовпадение откатывает транзакцию. Проверка действует и при последующих попытках изменить ссылки, но допускает удаление Build целиком по retention. Объекты блокируются по §3.3 и проверяются на `available`. Временные ссылки `output` не входят в это равенство и не изменяют снимок. JSONB не является единственным местом учёта ссылок для GC.

В этой же транзакции Build получает `queued`, фиксированные digest образа toolchain и настройки сборки. После коммита возвращается `202 Accepted` с `build_id` и ревизией. Редактирование Draft продолжается независимо. Снимок не меняется при обновлении задания и переживает рестарт воркера.

Воркер забирает задание через `FOR UPDATE SKIP LOCKED`, назначает `lease_token`, срок lease и номер попытки, затем освобождает транзакцию. Выполнение идёт вне транзакции; heartbeat продлевает lease. После истечения lease recovery возвращает задание в очередь либо завершает его после исчерпания попыток. Повторная попытка начинает pipeline заново по тому же снимку.

Любое изменение состояния воркером, включая регистрацию результата, проверяет актуальные token и срок lease. Просроченный воркер не может завершить сборку. Ошибки авторского кода завершают Build как `failed`; временные ошибки инфраструктуры повторяются с ограничением попыток и общей длительности. Доступны состояния `queued/running/succeeded/failed/cancelled`. Отмена отзывает lease; воркер прекращает Sandbox-процессы, а поздний результат не публикуется.

Допустимые переходы Build: `queued → running/failed/cancelled` и `running → queued/succeeded/failed/cancelled`. Возврат в `queued` разрешён recovery после закрытия попытки. Терминальные состояния не меняются; повторная сборка после них создаёт новый Build. Heartbeat не может продлить уже истёкший lease.

Завершение, отмена и recovery закрывают попытку под блокировкой Build: отзывают token и снимают только её удержания `output`, блокируя соответствующие объекты. Входные ссылки снимка сохраняются. Истечение срока загрузки результата завершает попытку инфраструктурной ошибкой, даже если её lease ещё действует. GC объектов не читает Build для решения о действительности lease: сначала recovery освобождает временные удержания, затем объект может быть удалён обычным протоколом.

## 6. Pipeline и публикация

1. Материализовать снимок и скачать его объекты в отдельный рабочий каталог с дисковой квотой. Проверить размеры и SHA-256 прочитанных объектов.
2. Скомпилировать выбранные компоненты и зависимости в Sandbox с зафиксированным toolchain.
3. Для каждого теста получить вход из ручного файла или генератора, запустить выбранный валидатор и подготовить ответ согласно явному режиму. Для `generated` проверить успешный запуск main solution и принятие полученного ответа чекером. Для `provided` проверить формат/принятие чекером; если задано main solution, дополнительно сверить с его ответом через checker. Без независимого решения истинность авторского ответа не гарантируется. Interactive-тесты проверяются совместным запуском решения и интерактора.
4. Сгенерировать `problem.yaml` исключительно из снимка. В готовом пакете все входы материализованы: Judge не запускает генераторы повторно. Сохранить исходники, ресурсы, настройки и исполняемые компоненты; Sandbox file ID не является содержимым пакета.
5. Записать ZIP во временный файл через `zip.Writer` и `io.Copy`, одновременно вычисляя SHA-256. Хеш окончателен только после успешного `Close` ZIP. Проверить пакет тем же контрактом формата, который использует Judge.
6. Зарегистрировать и загрузить ZIP как новый объект конкретной попытки по протоколу раздела 4. Финальная транзакция блокирует Build, затем объект по §3.3; проверяет `running`, актуальный lease, принадлежащее этой попытке удержание `output`, состояние `uploading`, срок и подтверждённый результат загрузки. Одним коммитом объект переводится в `available`, создаётся Package, снимается временное удержание и Build становится `succeeded`. Между временным удержанием ZIP и ссылкой Package нет отдельного коммита без владельца.

Падение до финальной транзакции оставляет незавершённую сборку и потенциально лишний объект; recovery закрывает попытку, а GC удаляет освобождённый объект. При неизвестном результате коммита воркер сначала перечитывает Build и его Package. Ограничение `UNIQUE(build_id)` исключает второй опубликованный Package этой сборки. После успешного коммита результат удерживает Package, а просроченный воркер не может изменить терминальное состояние Build.

Для каждой стадии заданы CPU, wall-clock, memory, process, output и disk limits; отдельно ограничены вся сборка и число её файлов/тестов. Диагностика содержит стадию, тест, CE/RE/TLE/MLE/OLE или инфраструктурную ошибку и ограниченный stdout/stderr с признаком обрезки. Выходной код процесса проверяется наряду со статусом Sandbox.

Авторский код выполняется без сети, credentials, Docker socket и доступа к файлам других сборок. Пути нормализуются, symlink и выход за рабочий каталог запрещены. Сетевые операции с S3 выполняет доверенный воркер вне Sandbox.

## 7. Память, окружение и воспроизводимость

Для крупных входов и выходов Sandbox нужен файловый транспорт с ограниченным буфером: загрузка файла, запуск по файловому идентификатору и скачивание результата. Текущие `Generate() []byte`, `Test(input []byte)`, сбор stdout в unary gRPC и `Storage.UploadFile` с `io.ReadAll` для этого пути заменяются. Доступность такого транспорта проверяется до реализации Builder.

ZIP, входы и ответы хранятся на диске с квотой; `tmpfs` не используется для крупных рабочих файлов. Multipart upload получает явные размер части и параллелизм. Ограничивается число одновременных загрузок и сборок. Небольшой текст можно читать целиком в рамках квоты; запрет самого имени `io.ReadAll` не является целью.

Потребление памяти зависит от ограниченных буферов, метаданных файлов и параллелизма, а не от суммы тел тестов. Это проверяется измерением heap/RSS на больших плохо сжимаемых данных. Временные файлы удаляются при завершении и при уборке каталогов брошенных попыток.

Сборка фиксирует digest toolchain, архитектуру/ABI, флаги, библиотеки и seed генераторов. Judge запускает компоненты в совместимом закреплённом окружении; бинарники из Sandbox экспортируются как файлы. Повторная компиляция компонентов текущим произвольным toolchain Judge не допускается.

Полный SHA-256 архива служит проверкой его байтов, а UUID — идентификатором Package. Первые восемь символов хеша показываются только в UI; при совпадении префикс удлиняется. Хеш не используется как номер ревизии или ключ авторизации. Порядок ZIP-записей и их timestamps нормализуются; побайтовая воспроизводимость компилятора не обещается.

## 8. Контесты и Judge

Контест закрепляет выбранный `package_id`; если UI предлагает пакет по умолчанию, это пакет максимальной ревизии Draft с успешной сборкой, а не последний завершившийся воркер. Параллельное завершение старой сборки не меняет выбор уже созданного контеста.

Условие, ресурсы, лимиты и scoring читаются из закреплённого Package/Build. Приём submission одной транзакцией читает закрепление контеста и создаёт submission с judge job, копируя в обе записи один `package_id`. Обычный rejudge берёт пакет из submission, а не из текущего состояния контеста; соответствие пакета задания и submission проверяется БД. Создание потребителя блокирует Package и фиксирует FK до освобождения блокировки, поэтому конкурирующее удаление не может оставить потребителя без пакета. Во время контеста замена пакета запрещена. Проверка по другой версии должна быть отдельной явной операцией, не меняющей историю исходной проверки.

Judge скачивает архив по ссылке из `stored_objects`, проверяет SHA-256 и использует уже собранные входы и компоненты. Внешние ключи не позволяют удалить Package, используемый контестом, submission или заданием проверки, включая историю.

## 9. GC и сроки хранения

Для `stored_objects` разрешены только переходы `uploading → available`, `uploading → deleting`, `available → deleting` и `deleting → deleted`. Возврат из `deleting/deleted` запрещён. Публикация и изменения ссылок подчиняются §3.3; GC состояний объектов блокирует только сами объекты, а очистка попыток выполняется отдельно по §5. Физический объект не удаляется до коммита `deleting`.

1. GC выбирает кандидата, затем в короткой транзакции `READ COMMITTED` получает его `FOR UPDATE`. **Отдельным SQL-запросом после получения блокировки** проверяются актуальное состояние, отсутствие всех рабочих и временных ссылок и срок удержания. Для `uploading` дополнительно должен истечь срок загрузки. Если условия выполнены, объект переводится в `deleting`. Пока блокировка удерживается, ни один писатель ссылок не может завершить конкурентное изменение. Любая оставшаяся ссылка, включая удержание попытки, запрещает удаление независимо от её возраста.
2. Вне транзакции GC удаляет объект S3. Ошибка или неизвестный результат оставляют `deleting` для повторной попытки. После подтверждения удаления запись становится `deleted`; этот UUID и ключ никогда не переиспользуются.
3. Запоздавшая загрузка может оставить данные под уже закрытым ключом, но не создать рабочую ссылку. Периодическая сверка S3 с реестром повторно удаляет объекты для `deleted` и обнаруживает объекты без записи. Срок хранения tombstone покрывает допустимое время запоздавших операций и сверки.

Корни удержания — Draft, сохранённые Build и Package, контесты, submissions и задания Judge. Удаление Package блокирует Build, Package и объект по §3.3 и проверяет все FK. Снятие ссылки и обновление `unreferenced_at` атомарны с удалением Package. Его Build сохраняется до удаления Package и окончания срока хранения диагностики; незавершённые Build не удаляются. Удаление терминального Build под его блокировкой освобождает ссылки снимка и попыток с блокировкой объектов; неизменяемость снимка не запрещает удаление Build целиком. Архив самодостаточен; для rejudge исходные блобы не нужны, но сохраняются, пока на них ссылается оставленный Build.

Retention для неиспользуемых объектов, терминальных Build и неподключённых Package задаётся явно в конфигурации развёртывания. Рабочие объекты не удаляются по возрасту S3. Lifecycle применяется к незавершённым multipart upload с периодом больше допустимой длительности загрузки. Для будущего production срок физического удаления согласуется с окном восстановления БД и резервными копиями объектов.

## 10. Реализация и проверка

1. Ввести целевую схему и Draft API с ревизиями, полным отображением конфигурации GFMT и квотами. Убрать редактируемый `problem.yaml`.
2. Реализовать файловый транспорт Sandbox, потоковое хранилище и протокол объектов вместе с GC.
3. Добавить Build со снимком, очередью PostgreSQL, lease/recovery и ограниченной диагностикой; реализовать pipeline и атомарную публикацию Package.
4. Перевести UI и Judge на закреплённые Package, новый формат и файловые операции. Удалить старое workspace-хранилище и сбросить старые тестовые данные.

Обязательные проверки:

- Правка метаданных или текста не читает тесты из S3 и не пересобирает ZIP.
- Редактирование во время запроса сборки даёт целостный снимок одной ревизии; retry использует тот же снимок.
- Набор входных UUID в JSONB-снимке точно совпадает с `problem_build_objects(role = input)`; ошибку соответствия нельзя закоммитить.
- Повтор HTTP-запроса и потеря ответа на коммит не создают дубликаты тестов, Build или Package.
- Падения после upload и до коммита, рестарт воркера, истечение lease и запоздалый результат не публикуют противоречивое состояние.
- Гонка GC с новой ссылкой или финализацией upload не удаляет рабочие данные; запоздавшая загрузка под закрытым UUID убирается сверкой.
- GC, ожидавший блокировку объекта, видит ссылки, закоммиченные за время ожидания; закрытие старой попытки не снимает удержания новой и не затрагивает снимок.
- Mixed tests, provided answers, interactive, зависимости подзадач и scoring одинаково интерпретируются Builder и Judge.
- Большие входы/ответы, переполнение вывода и диска, отмена и несколько сборок соблюдают ресурсные бюджеты; память не растёт пропорционально суммарному размеру тестов.
- Закреплённый пакет и его метаданные не меняются при редактировании Draft; GC сохраняет историю, нужную контестам и rejudge.
- Перед PR проходит `task precommit`.
